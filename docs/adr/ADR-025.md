# ADR-025: which aahp a workflow runs is its own doctor gate, and a shape that can run unpinned code fails

**Why it recurs:** a workflow copied into an adopting repository does not change when
the package does. Earlier shipped workflows, and hand edits of them, run the CLI in
ways the current templates no longer do: `npx -y @elvatis_com/aahp@<version>`, the
unscoped name through `npx` or `npm exec`, `node bin/aahp.js` copied from this
repository's own workflow, or the path form with the `npm ci` step edited out. None
of them is visible from inside AAHP, and the obvious place to put the check, the
`verify-workflow` gate, answers a different question.
**Decision:** `aahp doctor` carries a separate `cli-source` gate
(`scripts/check-cli-source.mjs`). `verify-workflow` asks whether a workflow can SKIP
the gate; `cli-source` asks whether the CLI a step runs is the package the
repository pinned, installed from its lockfile. Folding the two into one gate would
put two severities and two remedies behind one token, and a dashboard could not tell
a skippable gate from a stale copy.
**The severity rule:** a shape FAILS when it can execute code the lockfile did not pin
(`registry-fetch`, and `unowned-name` for every runner that downloads on a local
miss) or when it can never succeed (`checkout-path`, `no-install`). A shape that fails
CLOSED and only costs a request is ADVISORY: `npx --no-install aahp` after an install
step, where the `npx` binary cancels on a miss instead of executing and makes no
request when the package is placed (the measurement in ADR-013). It is still
reported, because the same line spelled `npm exec` executes the answer.
**No opt-in switch, and why it differs from `verifyWorkflow.enforce` (ADR-024 has the
same shape for trust decay):** `verify-workflow` fires on configurations some
repositories keep deliberately, and on a workflow the pull-request author may not be
allowed to edit, so it reports by default and blocks on opt-in. The failing
`cli-source` shapes are stale copies nobody keeps on purpose, each is a supply-chain
path into a required check or a step that is red on every run, and the fix is one
command in the same pull request: `aahp init --gates --workflows`, which rewrites only
the workflow files `aahp init --gates` manages and leaves `aahp.config.json` and
`package.json` alone. A 4.0.0 upgrade is where adopters meet it, with a migration note.
**Not flagged, on purpose:** this package itself (`self`, by `isSelfPackage`, since its
own workflows run `node bin/aahp.js` from the working tree); `node bin/aahp.js` where
the repository has that file, or under a `working-directory:` or `cd`; a missing
install when an earlier step uses an action other than checkout, setup-node or
setup-python, whose inside the reader cannot see; `npm run` indirection.
**Not covered, stated so a green gate is not over-read:** an `npm install --no-save`
of some other package followed by a local run; `yarn exec` and `pnpm exec`; installs
performed inside composite or reusable actions; workflow files outside
`.github/workflows/`; and whether any of these workflows is a required check at all.
A workflow that mentions `aahp` and cannot be parsed fails rather than skips, because
undecided is not clean.
